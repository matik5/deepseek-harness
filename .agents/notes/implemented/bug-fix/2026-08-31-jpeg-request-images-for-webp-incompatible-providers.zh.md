# Agent Note: 为不兼容 WebP 的提供方生成 JPEG 请求图片

Status: implemented

[English](2026-08-31-jpeg-request-images-for-webp-incompatible-providers.md) | 中文

## 问题

支持图片的 OpenAI 兼容提供方可能接受 PNG 与 JPEG，却让媒体解码器以 HTTP 400 拒绝 WebP。持久规范化可以合理地存储 WebP；路由请求变换也会在带 alpha 的 PNG 需要缩放或重新压缩时生成 WebP。因此，成功的 `read_image` 结果会先进入会话历史，下一次模型请求才失败；之后每个轮次都会重放同一份被拒绝的媒体。提供方模型元数据只声明图片模态，不声明可接受的图片媒体类型，所以适配器无法在第一次请求前协商格式。

## 决定

本地附件后端继续让持久规范化与提供方无关：预算内的干净 PNG、JPEG 与 WebP 仍按字节直通，必须保留 alpha 的规范化仍使用 WebP。模型请求投影使用独立兼容规则。预算内的 PNG 或 JPEG 原样直通；每个 WebP 附件以及每张需要按路由缩放或重新压缩的图片，都通过 85/75/60 质量阶梯编码为 JPEG。JPEG 转换把透明像素铺在白色背景上。请求变换版本为 `request-image-v6`；其身份记录 JPEG 质量与 alpha 背景，因此不会复用版本五的 WebP 缓存条目。

转换发生在适配器序列化内联 base64 或上传提供方文件之前。包括 DSHmux 在内的前端不检查或改写附件字节：内部工具结果和 DSH 发往提供方的请求都位于 Harness 进程中，而请求投影是聊天上传、`read_image`、压缩、直接 LLM 调用和提供方 Files 共同使用的唯一路径。

本决定部分取代[按 alpha 路由的图片质量阶梯记录](2026-08-24-alpha-routed-image-quality-ladders.zh.md)中的请求编码部分；其按 alpha 路由的持久规范化、固定质量阶梯、字节目标语义与总像素尺寸规则不变。本决定也更新[统一图片请求管线记录](../feature/2026-08-20-unified-image-request-pipeline.zh.md)中的确定性请求版本事实。

## 考虑过的替代方案

**在 DSHmux 内转换。** 否决：DSHmux 只把浏览器流量转发给 DSH，内部工具图片与 DSH 的提供方请求都不会经过这条转发。拦截它们需要带原生图片解码依赖的出站提供方代理，而且仍会漏掉不使用 DSHmux 的 Harness 客户端。

**只在提供方返回通用媒体解码 400 后重试。** 否决：提供方响应不会指出失败的是哪张图片或哪种媒体类型；不可见重试会让成功的模型输入取决于未记录的提供方响应；每个新变体还会额外消耗一次必然被拒绝的请求。

**把 WebP 转换为 PNG 并保留 alpha。** 否决：观察到的端点也曾拒绝持久引用为 PNG 的请求图片，因为路由缩放把它们重新编码成 WebP；JPEG 是该部署需要的共同格式。持久历史继续保留透明度，供之后的路由使用。

## 后果

- OpenAI 兼容后端只需为经过变换的请求图片解码 JPEG，不再需要为 Harness 生成的请求解码 WebP。
- 透明 WebP 或任何超过路由请求预算的透明图片会以白色背景合成后到达模型。其持久规范化附件保留 alpha，未来的投影策略仍可使用。
- 已有请求图片缓存会按 `request-image-v6` 重新生成；持久附件 ID 与会话日志不变。
- 聚焦附件测试覆盖预算内 WebP 转换、alpha 合成元数据、缓存校验、路由缩放和未改变的规范化图片路径。Blender 复现中，`render_full.png` 持久存为 WebP，但会在 pi-ai 序列化前投影为 1280×960 JPEG。
